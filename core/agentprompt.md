## AGENT FAILURE GUARDRAILS (violations cause task failure)

- **MAX RETRIES**: If an action fails twice (same URL, same command), do not retry — skip and move on. Never retry more than twice.
- **NO BACKGROUND POLLING**: Each Bash call is independent and stateless. Never background a process with `&` and poll for results with `sleep && cat`. Read output directly from each command's return value. This also covers AUTO-backgrounded calls: when the harness reports a command "did not complete within its timeout and was moved to the background", do NOT poll its output file in a loop. Continue other work and read the output file ONCE at the point you actually need the result (or once before finishing); if it is still incomplete then, proceed without it and record the command as failed — no further waiting or re-checking. (A correctly-prefixed agent-browser call never reaches this state — the coreutils timeout kills it first.) Also never use `sleep` to wait for anything: a sleep-prefixed command is never auto-backgrounded — it blocks for its full duration, and some builds reject it outright.
- **NO BLIND TOOL SWITCHING**: Before switching tools (e.g. agent-browser → Puppeteer scripts), state in one sentence what specifically failed and why the new tool fixes that. If you cannot state a specific reason, do not switch.
- **CONTEXT SCOPE**: Only files you created in this session are relevant. Ignore file paths from prior agent runs visible in context.

## ENFORCED RULES (violations cause task failure)

- **SERPAPI FIRST**: Before any `npx agent-browser open` call for a specific entity's page (a company, product, listing, document), use SerpAPI to get the exact URL. Never guess slugs.
- **SNAPSHOT NOT SCREENSHOT**: Use `snapshot -i` for navigation. Screenshots (`screenshot /tmp/x.png`) only for sending to Telegram. Never read a screenshot to navigate.
- **TUNNEL**: For a long or multi-step browser flow that must not be interrupted (so the tunnel is ready by the time Puppeteer finishes): background `$CLAUDE_HOME/browser-viewer/start-tunnel-bg.sh` BEFORE Puppeteer, then get token inline after. For all other interventions (bot check, OTP, etc.): `LINK=$(bash $CLAUDE_HOME/browser-viewer/start-tunnel.sh "url" "$AGENT_KEY")` INLINE — takes ~15s, never background.
- **FORM PATTERNS**: Read `docs/form-patterns.md` before filling any form.
- **BATCH COMMANDS**: Chain sequential commands with `&&`. Never separate open/wait/snapshot into 3 tool calls.
- **SESSION ISOLATION**: Every `agent-browser --cdp 9222` command MUST include `--session <task>-<rand>` where `<task>` is a short descriptor and `<rand>` is a 4-char random suffix. Generate the suffix once at the start of your session: `SID=$(cat /dev/urandom | tr -dc 'a-z0-9' | head -c4)` then use it in every command (e.g. `--session hotels-$SID`, `--session flights-$SID`). This guarantees uniqueness even when multiple agents run the same task type concurrently. Multiple agents share one Chrome instance — without a unique `--session`, they fight over the same tab and destroy each other's page context. Never omit `--session`.
- **HARD TIMEOUT**: Prefix EVERY agent-browser invocation — `npx agent-browser` or bare `agent-browser`, including commands copied from SKILL.md examples — with coreutils `timeout -k 10 90`, e.g. `timeout -k 10 90 npx agent-browser --cdp 9222 open "$URL" --session x-$SID && timeout -k 10 90 npx agent-browser --cdp 9222 snapshot -i --session x-$SID`. This kernel-enforces a 90s wall-clock cap per invocation (SIGKILL 10s later), killing the whole process tree. The coreutils prefix is the ONLY kill mechanism you have: the Bash tool's `timeout` PARAMETER never kills anything — per Claude Code's documented design it is a stop-waiting threshold (the command is moved to the background and runs to completion), and on some builds it doesn't even stop the wait (a wedged daemon once held a Bash call — and with it the entire session — for 78 minutes despite a 60s tool timeout, issue #492). Never rely on the tool parameter to bound a process; always use the coreutils prefix. For an operation you EXPECT to run long (large `wait --download`, `record`, a slow site where you raised `AGENT_BROWSER_DEFAULT_TIMEOUT`), raise the cap to comfortably exceed the expected duration (e.g. `timeout -k 10 300`) — never omit the prefix. If a call is killed at the cap (exit 124/137): retry ONCE with a doubled cap only if the operation plausibly needed more time; a second kill, or any failure mentioning `os error 11` / "daemon may be busy", means the daemon is wedged — permanent failure for that browser session, do NOT retry further (MAX RETRIES applies), fall back to SerpAPI/WebSearch. EXCEPTION — restart window: a signal/connection death NOT explained by your cap (exit 143, or 137 well before your cap elapsed, or "connection refused") usually means Chrome and agent-browser were restarted underneath you (nightly, or a health respawn); that is transient, not a wedge — wait ~15s for the browser to come back, then retry once.
